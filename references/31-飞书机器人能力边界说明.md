# 飞书机器人能力边界说明

## 一句话结论

飞书机器人**不能单独运行**多网盘下载 Skill 的全部功能。它是“遥控器”，真正下载靠一台常开的电脑/NAS 上的 **pan.py serve 下载服务**。

## 当前飞书桥的真实工作方式

`scripts/feishu_bot.py` 只做三件事：
1. 收到飞书消息 → 提取链接和“提取码/密码/pwd”后的 4-6 位码；
2. 把它 **转发** 给本机/NAS 的下载服务地址（`POST /api/download`）；
3. 把下载服务的返回结果（“已开始下载”或错误）回给飞书。

真正执行下载、重试、断点续传、授权、实时速度的，都是**那台常开设备上正在运行的 `pan serve`**，不是飞书机器人本身。

## 能/不能清单

| 环节 | 飞书机器人能否单独完成 |
|---|---|
| 收你的链接 | ✅ 能 |
| 识别网盘、提取提取码 | ✅ 能（桥内置正则） |
| 真正下载文件 | ❌ 不能，依赖常开的下载服务 |
| 扫码/网页授权 | ❌ 不能，在下载服务那台机器上完成 |
| 看实时速度/进度 | ✅ 能（机器人回给你 /live 地址，网页也由下载服务提供） |
| 下载到 NAS/远程设备 | ❌ 不能，需要该设备运行服务 |

## 最少运行架构

```
飞书机器人（收命令 / 回消息）
        │ 转发 POST /api/download
本机/NAS 常驻 pan.py serve（真正下载 + 实时进度 + 授权）
```

## 常见误解纠正

- “我把飞书机器人启动起来就能下文件” ❌ 不行。
- “机器人收到链接后自动到某个网盘会员账号里下载” ❌ 不承诺，授权和风控在服务端。
- “飞书机器人能在无公网时收到消息” ⚠️ 事件回调需要公网地址（或升级长连接接入），当前版本依赖回调/隧道。

## 怎么理解这个设计

这样分工是故意的：下载要在**有网盘授权、有磁盘、常开**的设备上完成；飞书只是让你“从手机上遥控它”。安全性也更好——密码、Token、Cookie 都存在那台设备上，不经过飞书云端。
